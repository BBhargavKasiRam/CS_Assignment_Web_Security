Vulnerable Query Structure

            
// Vulnerable route: string concatenation
const sql = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`;

// When attacker inputs username: admin' --
SELECT * FROM users 
WHERE username = 'admin' --' AND password = 'arbitrary';
                         └─► SQL COMMENT: Entire password check is ignored!

            

              Root Cause: User data breaches the boundary between code and data. The single quote (') terminates the username literal, and the double dash (--) signals SQLite to treat all subsequent text on that line as a comment. The database evaluates only WHERE username = 'admin', immediately bypassing password authentication.
            

          


          

            
Secure Parameterized Query

            
// Secure route: prepared statement with ? placeholders
const stmt = db.prepare('SELECT * FROM users WHERE username = ? AND password = ?');
const user = stmt.get(username, password);

// Injected input: admin' --
// Evaluated literally as:
WHERE username = "admin' --" AND password = "arbitrary"
└─► Treated as literal string data. No user with literal name "admin' --" exists.

            

              Why Mitigation Works: The query structure is compiled and locked by the database engine prior to binding parameters. The runtime data values can never alter the query's Abstract Syntax Tree (AST). The attack fails deterministically.
            

          

        

      


      
      

        

          

            Per the assignment syllabus (Table 2e), one primary defense is implemented in code (Parameterized Queries), while the three complementary defense strategies are detailed below:
          


          

            

              

                1
                
Parameterized Queries (Implemented)

              

              

                The primary defense against SQL injection. Separates SQL code from untrusted data at the engine level. By preparing the statement first and passing values via placeholders, user data is strictly parsed as column values and can never be interpreted as executable SQL syntax.
              

            


            

              

                2
                
Input Validation with Allow-Lists (Defense-in-Depth)

              

              

                Enforces strict syntactic constraints (e.g., regex allow-listing alphanumeric usernames ^[a-zA-Z0-9_]{3,20}$). While allow-listing provides strong defense-in-depth and rejects malformed requests early, it does not replace parameterization because business requirements often require special characters (apostrophes in names, punctuation in addresses).
              

            


            

              

                3
                
Least-Privilege Database Accounts

              

              

                The web application's database service account should only possess the minimum permissions necessary for its role (e.g., restricted SELECT and UPDATE on specific application tables; no DROP TABLE, GRANT, or administrative procedures like ATTACH DATABASE or xp_cmdshell). This limits exploit blast radius if injection occurs.
              

            


            

              

                4
                
Safe Error Handling & Logging

              

              

                Database syntax exceptions, schema details, and engine errors must never be printed to end-user HTTP responses. Internal exceptions should be logged to secure server-side monitoring, while clients receive only generic status responses (e.g., "Invalid credentials" or "Service unavailable"), preventing error-based reconnaissance.
